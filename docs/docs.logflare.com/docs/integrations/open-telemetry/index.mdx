Logflare features OpenTelemetry integration to ingest directly from OpenTelemetry SDKs.

:::note
This feature is under development and is considered alpha stage. It is not advisable to use it for mission critical production workloads.
:::

The ingestion url is `https://otel.logflare.app:443`.

Supported ingestion formats:

- http/protobuf
- http/json
- grpc/protobuf

Non-finite numeric values are represented as the strings `"NaN"`, `"Infinity"`, and `"-Infinity"` in converted event bodies and JSON output. ClickHouse numeric columns retain their IEEE 754 non-finite Float64 values when encoded as RowBinary.

### Trace event correlation

Trace and span IDs use lowercase hexadecimal. Standalone log records created from
span events include the containing span's `span_id` and `trace_id`, so you can
correlate those event logs with their traces.

### Trace payload fields

Span records retain their status, trace state, links, nested events, flags, and
counts of dropped attributes, events, and links. Status codes are stored as
`UNSET`, `OK`, or `ERROR`. Span events also continue to produce standalone log
records, whose `trace_flags` contain the containing span's W3C trace flag bits.
Resource and scope schema URLs are kept separately from user-supplied attributes.

An empty HTTP/protobuf body represents an empty batch. It follows the same authentication and source checks as a non-empty request.

HTTP ingestion applies the configured parser body limit to both protobuf and JSON requests, including decompressed request bodies. The default OTLP pipeline limit is 12 MB.

OTLP JSON uses hexadecimal `traceId` values (32 characters) and `spanId` / `parentSpanId` values (16 characters), including identifiers in span links and metric exemplars. Hexadecimal characters may use either case. Empty optional identifiers are accepted; malformed non-empty identifiers are rejected. `AnyValue.bytesValue` continues to use Base64 encoding.

HTTP ingestion responses use the request encoding: `application/json` requests receive JSON, and `application/x-protobuf` requests receive binary protobuf. Ingestion errors use the same encoding for their Google RPC Status response.

When the ingestion spool is temporarily unavailable, HTTP OTLP endpoints return `503 Service Unavailable` with `Retry-After: 5`. Exporters should retry the batch after that delay.

### gRPC ingestion failures

When the source cannot start or the ingest spool is unavailable, OTLP/gRPC returns
`UNAVAILABLE`. Exporters should retry the batch with backoff. An unexpected ingest
failure returns `INTERNAL` instead of a successful acknowledgement.

### Validation responses

OTLP HTTP authentication, request parsing, body-size, and ingestion failures use a Google RPC Status response in the request's JSON or binary protobuf encoding. The HTTP status is preserved, including `401` for missing credentials, `400` for malformed payloads, and `413` for oversized bodies. The response's `code` identifies the corresponding Google RPC error category.

Unexpected ingestion failures return HTTP `500` with a Google RPC Status body in the request encoding. They never return a successful acknowledgement of the batch.

OTLP/HTTP and OTLP/gRPC responses include `partial_success` when validation rejects
telemetry. The response reports the number of rejected log records, metric data
points, or spans, plus an error message. A span counts once if either its span
record or any derived event record fails validation, even when several records
from that span fail. Events with timestamps more than one hour in the future
are included in the rejected count. Source rules that intentionally filter events
do not count as validation rejections.

A batch whose every input is rejected also returns partial success. As required by
OTLP, exporters must not retry these responses. Fully accepted batches leave
`partial_success` absent.

Metric data points rejected during conversion also appear in `rejected_data_points`,
including gauge or sum points without a numeric value and unsupported summary
points. Valid sibling points are still accepted. Metrics without data points do
not add rejections. Points marked `NO_RECORDED_VALUE` remain intentionally omitted
as missing observations and do not count as rejected samples.

### Testing OpenTelemetry ingestion locally

Clone the Github repo, and then run the following:

```bash
# for bq backend
docker compose -f docker-compose.yml -f docker-compose.latest.yml up -d db logflare
# for pg backend
docker compose -f docker-compose.yml -f docker-compose.pg.yml -f docker-compose.latest.yml up -d db logflare
```

1. Create a new source to populate the `x-source` header with the source UUID.
2. Use the api-key found in `.docker.env` and set it to `x-api-key` header
3. Set the otlp endpoint to `http://localhost:50051`
4. Start your OpenTelemetry instrumented app.

### Limitations

- Only **traces** and **metrics** are currently supported.

### Metric conversion

- Exponential histogram `zero_count` records the number of zero-valued observations independently of histogram `scale`.

- Exponential histograms may omit positive or negative buckets. Omitted buckets are stored with offset `0` and an empty bucket-count array.

- Metrics without a data payload and gauge or sum points without a value are omitted. Valid points in the same batch, including zero values, are still ingested.

- Metric points marked `NO_RECORDED_VALUE` are omitted as missing observations. Other points retain their original `flags` bitmask.

- Metric aggregation temporality accepts protobuf enum names and integer values. Unknown enum values are stored as `unspecified`.

- Metric descriptions are stored in `description`, and metric-level metadata is stored in `metric_metadata` separately from Logflare event metadata.

- Metric exemplars retain their values, timestamps, filtered attributes, and hexadecimal trace and span IDs. Exemplars without a value are omitted.

- Non-finite metric numbers are stored as the JSON-compatible strings `NaN`, `Infinity`, and `-Infinity`; finite numbers and absent optional fields retain their original values.

### Timestamp precision

OTLP timestamps use nanoseconds regardless of the number of digits. Logflare stores its event timestamp in microseconds and retains supplied nanoseconds in `time_unix_nano`, with `start_time_unix_nano` and `end_time_unix_nano` retained where applicable. Logs with no event time use their observed time; missing times otherwise use the ingestion time.

The default ClickHouse mapping prefers the original nanoseconds. Its signed 64-bit `DateTime64(9)` columns saturate at `9223372036854775807` for later OTLP timestamps; the original unsigned value remains in the event body. NDJSON output intentionally emits microseconds, including unsigned timestamps beyond the ClickHouse nanosecond range.
